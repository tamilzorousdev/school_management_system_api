# School Management API guide

For the Flutter team and anyone calling the API. Swagger has every endpoint with examples. Flutter team: `http://<server>:3000/api/docs/mobile` (JSON at `/api/docs/mobile-json` for code generators). Web team: `http://<server>:3000/api/docs/admin`.

## One API, one database

The Admin web and the Flutter app (Staff, Parent and Driver roles) call the same API and read the same tables. There is no separate mobile database. A mobile endpoint is a role-specific view over the same records the admin web edits.

## Base URL and versions

- Base: `http://<server>:3000/api/v1`
- `v1` is the current version. A `v2` route is added only for a breaking change, and `v1` keeps working next to it. Call `v1` unless a document tells you otherwise.
- Health without a version: `GET /api/health`

## Route families

| Prefix                                                      | Used by                                                        |
| ----------------------------------------------------------- | -------------------------------------------------------------- |
| `/auth`                                                     | Every app: OTP sign-in, refresh, sign-out                      |
| `/me`                                                       | Every app: profile, language, push device, notification centre |
| `/mobile/parent/*`, `/mobile/teacher/*`, `/mobile/driver/*` | Flutter role screens (added module by module)                  |
| `/admin/*`                                                  | Admin web                                                      |
| `/admin/fleet/*`                                            | Admin web: live bus status (read from the Telematics service)  |
| `/files`                                                    | Uploads and signed downloads                                   |

## Sign-in flow

Sign-in uses the central **Tamilzorous Auth Service** for the OTP (`AUTH_PROVIDER=central`). The app still calls only this API; nothing changes in the app:

- `POST /auth/otp/request`: we check the number is an active user here, then the Auth Service sends the SMS (valid **15 minutes**, resend after 30 seconds). A user the Auth Service does not know yet is registered there automatically on this first request (name, mobile, email; staff and parents without an email get `firstname.lastname.1234@school.tamilzorous.com`).
- `POST /auth/otp/resend`: the **Resend OTP** button. Same body and checks as `otp/request`, calls the Auth Service `resend-otp`. Use it once `resend_in` has passed; too early gives `429 OTP_RESEND_TOO_SOON`.
- **Auto-read OTP on Android:** send `"app_hash": "Xy12AbCd3Ef"` (the 11-character SMS Retriever hash of the app build) in `otp/request` and `otp/resend`. The Auth Service adds it to the SMS so the app fills the code itself. Leave it out on iOS and the web. A wrong format gives `400` on `app_hash`. The old name `app_signature` still works.
- `POST /auth/otp/verify`: the Auth Service checks the code; this API then issues the school session (`access_token`, `refresh_token`) with school and roles.
- `POST /auth/refresh` also renews the Auth Service sign-in (its refresh token is kept encrypted on our session). If the Auth Service says the sign-in has ended, the answer is `401 SESSION_REVOKED` and the user signs in again; if it cannot be reached, `503 AUTH_SERVICE_UNAVAILABLE` and the app can retry. `POST /auth/logout` signs out here and at the Auth Service. Apps keep using only this API's tokens.
- Deactivating a user here blocks OTP and ends every session at once.

### Which app can sign in

Send the app on both calls: `"app": "mobile"` in `/auth/otp/request` and `"client": { "app": "mobile", ... }` in `/auth/otp/verify` (the admin web sends `"admin"`). `client.app` is required.

| `app`              | Who can sign in                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------- |
| `mobile` (Flutter) | Users with a Parent, Teacher, HOD, Driver, Attendant, AO, Warden or Assistant warden role |
| `admin` (web)      | Users with Super admin, Admin, Principal, AO or Transport in-charge                       |

An AO gets `mobile_apps: ["office"]` and opens the **Office** home in the app (see _AO office: wings_ below).

Anyone else gets `403 APP_NOT_ALLOWED` at the OTP request, so no SMS is sent.

### One app, switch roles inside it

A person cannot be both teaching staff (Teacher, HOD) and bus crew (Driver, Attendant): assigning both returns `400 VALIDATION_FAILED` on `role_codes`. Parent can be combined with either.

One person, one sign-in. A number that is both a parent and a teacher signs in once; the profile (`data.user` in the sign-in response, or `GET /me`) says which sections they can open:

```json
"mobile_apps": ["staff", "parent"],
"sections": [
  { "app": "staff",  "label": "Staff",  "mobile": true, "roles": [{ "code": "TEACHER", "name": "Teacher", "app": "staff" }] },
  { "app": "parent", "label": "Parent", "mobile": true, "roles": [{ "code": "PARENT",  "name": "Parent",  "app": "parent" }] }
]
```

- One entry in `mobile_apps`: open that home directly.
- Two or more: show a chooser once, remember it on the phone, and offer "Switch to Parent / Staff" in the profile menu.
- Switching needs no new OTP and no new token: the same `access_token` works for `/mobile/parent/*` and `/mobile/teacher/*`.

1. `POST /auth/otp/request` with `{ "mobile": "9876543210", "app": "mobile", "app_hash": "Xy12AbCd3Ef" }` (`app_hash` on Android only). Returns `expires_in` and `resend_in` (seconds) for the countdown; the Resend button calls `POST /auth/otp/resend` with the same body.
2. `POST /auth/otp/verify` with `{ "mobile": "...", "otp": "123456", "client": { "app": "parent", "platform": "android", "device_name": "Pixel 7", "app_version": "1.0.0", "fcm_token": "..." } }`.
3. Store `access_token` and `refresh_token` securely. Send `Authorization: Bearer <access_token>` on every call.
4. Read `user.apps`. If it has more than one value (for example `["staff", "parent"]`), show a role picker. Otherwise open that app directly.
5. When any call returns `401` with `error: "TOKEN_EXPIRED"`, call `POST /auth/refresh` with the refresh token, store **both** new tokens, and retry once. Any other 401 (`SESSION_REVOKED`, `SESSION_INVALID`, `ACCOUNT_INACTIVE`, `TOKEN_INVALID`) means: go to the login screen.
6. On sign-out call `POST /auth/logout`. It ends the session and stops push to the device.

## Response format

Success:

```json
{ "status": 200, "message": "OK", "data": {} }
```

List (`data`):

```json
{ "items": [], "total": 42, "page": 1, "limit": 20, "total_pages": 3, "has_next": true }
```

List query parameters: `page` (from 1), `limit` (1 to 100, default 20), `search`, `sort`, `order` (`asc` or `desc`) plus the filters each list documents. Unknown parameters are rejected, so send only documented ones.

Error:

```json
{
  "status": 400,
  "error": "VALIDATION_FAILED",
  "message": "mobile must be a valid 10-digit Indian mobile number",
  "errors": [{ "field": "mobile", "message": "mobile must be a valid 10-digit Indian mobile number" }]
}
```

Show `message` to the user. Use `error` to decide what to do. Use `errors[].field` to highlight form fields.

## Field conventions

- Field names are `snake_case`.
- IDs are integers.
- Dates are ISO 8601 with the India offset, for example `2026-11-02T09:15:00.000+05:30`.
- Mobile numbers are 10 digits. The API accepts `+91 98765 43210` and stores `9876543210`.
- `language` is `en` or `ta`. Notifications arrive in the user's language.
- Every response carries an `X-Request-Id` header. Include it when you report a bug.

## Push notifications

- Register the device after sign-in (or pass `client.fcm_token` in verify): `POST /me/devices` with `fcm_token`, `platform`, `app`. Call it again whenever Firebase gives a new token.
- Remove on sign-out: handled by `POST /auth/logout`. To remove a token alone: `DELETE /me/devices?fcm_token=...`.
- Push `data` always has `notification_id`, `category` and `template`, plus the values used in the message (for example `bus`, `stop`, `minutes`). Use `category` to open the right screen.
- The notification centre is `GET /me/notifications` (in-app copy of every message), `GET /me/notifications/unread-count`, `PATCH /me/notifications/{id}/read` and `POST /me/notifications/read-all`.

## Which school

Every school user belongs to one school, and the API reads it from the token. The super admin belongs to none: on `/admin/*` school pages they send `X-School-Id: <id>`, or the API answers `400 SCHOOL_REQUIRED`. The Flutter apps never send this header.

### School logo

`GET /me` returns `school: { id, name, code, logo_url }`. Show `logo_url` on the app header and splash; it is `null` when the school has no logo. The link is signed and expires after `FILE_URL_TTL_SECONDS` (1 hour), so take it from a fresh `/me` instead of caching it.

The admin web sets it in School setup → School profile: `POST /files` (purpose `school_logo`, PNG/JPG/WEBP), then `PATCH /admin/school { "logo_file_id": <id> }`, or `null` to remove it. A file that is not an image returns `400 VALIDATION_FAILED` on `logo_file_id`. ID cards, fee receipts, payslips and TCs print the same logo.

### Student ID card design

`GET /admin/school` returns `id_card_design` (`design1`, `design2`, `design3` or `custom`), plus `id_card_front_file_id`, `id_card_front_url`, `id_card_back_file_id`, `id_card_back_url` and `id_card_layout` for the school's uploaded design.

`custom` is the full ID card design made by the school's design team. The admin web uploads it in School setup → Student ID card: a PDF is turned into one PNG per page in the browser (page 1 front, page 2 back), and PNG or JPG files go as they are. Each image goes to `POST /files` with purpose `id_card_design`, then `PATCH /admin/school { "id_card_front_file_id": 51, "id_card_back_file_id": 52, "id_card_design": "custom" }`. Send `null` to remove a side. A file that is not an image of this school returns `400 VALIDATION_FAILED`, and choosing `custom` without a front side returns `400` on `id_card_front_file_id`.

`id_card_layout` says where each student's details go on the design: `{ "front": [...], "back": [...] }`, each item `{ key, x, y, w, h, font_size, color, bold, align }`. `key` is one of `photo`, `qr`, `student_name`, `admission_no`, `class_section`, `roll_no`, `dob`, `blood_group`, `guardian_name`, `guardian_mobile`, `address`, `academic_year`, at most once per side. `x`, `y`, `w`, `h` are fractions (0 to 1) of the card width and height, `font_size` is in points (long values shrink to fit the box), `color` is `#RRGGBB`. The admin web sets a starting layout on the first upload and the admin drags the boxes into place. An unknown key or a bad colour returns `400 VALIDATION_FAILED` on `id_card_layout`.

When `id_card_design` is `custom`, `GET /admin/students/{id}/id-card` and `GET /admin/id-cards` print the uploaded front and back at ID card size (54 × 85.6 mm, portrait or landscape from the image) with each student's photo, details and boarding QR in the layout positions. Transparent areas of the design print white. Pass `?design=custom` to print it before it is in use.

### Combine class (instead of a proxy)

When no teacher should take the period, the AO can send the students to other sections of the same class that have a period running at that time with a teacher in:

### Emergency broadcast

An urgent message from the school office to all parents, all staff, everyone, or the parents of chosen classes, sections or students (optionally with their teachers). School admin, Principal and AO can send it (`emergency.send`) and see the history (`emergency.view`). School admin and Principal also have `emergency.approve`.

**Approval.** A broadcast to the whole school (`everyone`, `parents`, `staff`) or with SMS, sent by someone without `emergency.approve` (for example the AO), waits with `status: pending_approval`; admins and the principal get `EMERGENCY_APPROVAL_NEEDED` (push). Approving sends it (or schedules it for its `send_at`); rejecting needs a note. The sender gets `EMERGENCY_REVIEWED`.

**Schedule and expiry.** `send_at` sends later (1 minute to 60 days ahead, `status: scheduled`). `expires_in { value, unit }` with `unit` = `seconds`, `minutes`, `hours`, `days`, `months` or `years` (5 seconds up to 5 years) takes it off every screen when the time is up, counted from when it goes out: pushes and SMS not sent yet are dropped, the push carries a time-to-live so phones that were offline do not get it late, the in-app notification leaves the bell list (`status: expired`), and apps get the socket event `emergency.ended { broadcast_id, reason, ended_at }`. Messages already in a phone's notification tray stay there. `POST /{id}/end` does the same at once (End now). A follow-up with `category: all_clear` ends the broadcast it follows up.

Every broadcast has `state`: `pending_approval`, `scheduled`, `active` (on screen), `expired`, `ended`, `rejected` or `cancelled`, plus `send_at`, `expiry { value, unit, label }`, `expires_at`, `ended_at`, `end_reason` (`expired`, `ended`, `all_clear`), `ended_by`, `reviewed_by`, `reviewed_at`, `review_note`.

**How it is delivered.** On send, the API saves one row per person first (a parent with several children gets one message that lists them), then delivers in the background: an in-app notification at once (category `alert`), a live socket event `emergency.alert { broadcast_id, title, message, category, severity, sent_at }` to everyone with the app open, push to app users and SMS to every mobile number, including parents without the app. Push and SMS each get up to 3 tries (10 s, 30 s, 90 s apart); after a restart the API carries on with whatever was not sent. Tamil readers get the Tamil title and message when given. Push follows `PUSH_AUTO`: while it is `false` the push is marked not sent and the in-app, socket and SMS still go out. SMS goes through Kafka with template `school_emergency_broadcast` (`_ta` for Tamil), variables `school`, `title`, `message`, `name`.

### Digital signature (sign on screen or photo)

Teachers, parents and the school have two ways to sign. Both are saved as a clean transparent PNG (`mime_type: image/png`, up to 900 px wide, cropped tight to the ink), so report cards, receipts and payslips look the same either way.

1. **Sign here (signature pad in the app).** The app shows a white pad; the person signs with a finger or stylus. Export the pad as a PNG (transparent or white background, dark ink) and upload it with `POST /files` (multipart `file`, `purpose: "signature_pad"`). The API keeps the strokes, removes the background and crops it. An empty pad gives `400 SIGNATURE_NOT_FOUND` ("The signature pad is empty").
2. **Upload photo (signed on paper).** Sign with a dark pen on white paper and take a photo; upload with `purpose: "signature"` (`teacher_signature`, `parent_signature` and `school_signature` work too). The API fixes the rotation and removes shadows, the paper and ruled lines, keeping only the ink in the pen's colour. A photo without ink gives `400 SIGNATURE_NOT_FOUND`.

Then save the file id with `PUT /mobile/teacher/signature` or `PUT /mobile/parent/signature` `{ "signature_file_id": 42 }` (school: `PATCH /admin/school` `{ signature_file_id }`). Other upload purposes keep their format. `GET` on the same paths returns the current signature and its `history` (newest first).

**Teacher and parent signatures are separate.** One person who is both a teacher and a parent has two signatures. Saving one never changes the other, with one exception: the first time they save a teacher signature while the Parent app one is empty, it is copied there. The save answers `{ signature_file_id, signature_url, parent_signature_copied, message }`; show `message` when it is not null:

| Saved from | When                       | `message`                                                                        |
| ---------- | -------------------------- | -------------------------------------------------------------------------------- |
| Staff app  | first time, copied         | This signature is also set for your Parent app. You can change it there anytime. |
| Staff app  | Parent app already has one | Your Parent app signature stays the same. Change it in the Parent app.           |
| Parent app | the parent is also staff   | Your Staff app signature stays the same. Change it in the Staff app.             |

**On report cards.** A box shows a signature only after that person signs the card (`teacher_signed`, `parent_signed`). When someone changes their signature, cards they already signed **this academic year** switch to the new one and get `teacher_signature_updated_at` / `parent_signature_updated_at`; the PDF prints "Signed 12 Nov 2026 · updated 16 Nov 2026" under the box. Earlier years never change. Removing a signature leaves signed cards as they are, and signing again needs a signature (`400 NO_SIGNATURE_UPLOADED`).

**Admin web.** `GET`/`PUT /admin/staff/{id}/signature` (`staff.view` / `staff.manage`) and `GET`/`PUT /admin/guardians/{id}/signature` (`students.view` / `students.manage`) show and set or remove the signature for that person. Every add, change and removal is kept in `history` with `action` (`added`, `changed`, `removed`), the old and new image, `changed_by`, `by_admin` and `at`. When the office changes it, the owner gets an in-app note (`SIGNATURE_SET_BY_SCHOOL`). When a parent changes or removes their own signature, their children's class teachers and the school admin and principal get an in-app note (`PARENT_SIGNATURE_CHANGED`). Neither sends push or SMS.

**Use an earlier signature again.** Each `history` row has `can_use_again` (its image is not the current signature). `POST /mobile/teacher/signature/history/{changeId}/use` or `POST /mobile/parent/signature/history/{changeId}/use` (admin: `POST /admin/staff/{id}/signature/history/{changeId}/use` and `POST /admin/guardians/{id}/signature/history/{changeId}/use`) makes that image current again with no new drawing or photo. It answers like the save (`message` included), is recorded as `changed` with the note "Used an earlier signature again", and report cards signed this year switch to it. A row of another person gives `404 SIGNATURE_CHANGE_NOT_FOUND`; the current one gives `400 SIGNATURE_ALREADY_IN_USE`.

### Two attendance sessions a day

Student attendance is taken in the **1st period (`session: "morning"`)** and the **5th period (`session: "afternoon"`)**; they are stored as periods 1 and 5. The old `period` field still works (0 or 1 = morning, 5 = afternoon); any other period gives `400 PERIOD_NOT_ALLOWED`.

**Session-wise or period-wise.** The school picks it in School profile (`attendance_mode` on `PATCH /admin/school`):

| `attendance_mode`   | How attendance is taken                                                                                            | What the app sends                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `session` (default) | Twice a day: 1st period (morning) and 5th period (afternoon)                                                       | `session`; other periods give `400 PERIOD_NOT_ALLOWED`                                   |
| `period`            | Every teaching period of the bell schedule; the teacher of that period in the timetable (or the proxy) can mark it | `period` = 1 to the last period; beyond the bell schedule gives `400 PERIOD_NOT_ALLOWED` |

Every roster and board answer has `mode`, `session` and `period`. The `/current` endpoints pick the period running now in either mode, so the Staff app needs no change if it uses them. In period mode a later period starts from the marks of the period before, the grace minutes apply after each period, reminders go to the teacher of that period, and the day status is the average of all periods (all present = present, all absent = absent, otherwise half day).

- **The day** comes from both sessions: both present = `present` (`late` if either was late), absent in one = `half_day`, absent in both = `absent`, leave in both = `leave`. Reports, percentages, the parent calendar, today's badge, the report card and bus no-shows all use the day.
- **Teachers** can save a session only **today during its period**: morning in the 1st period, afternoon in the 5th (bell times from the timetable). Before it: `400 SESSION_NOT_OPEN`; after it or on an earlier day: `400 SESSION_CLOSED`. The office (AO, admin) can save any session at any time, so a missed session is marked by the AO.
- **Absent alert**: once per student per day. Absent in the morning → alert; present in the morning and absent in the afternoon → alert "(afternoon)".
- Parent `GET /mobile/parent/children/{id}/attendance/today` and each day of the month calendar now also return `morning` and `afternoon`.

### Attendance time window, grace and missed

## Routes, stops and timings (admin web, Parent and Driver apps)

**Route timings.** Every route (`GET /admin/transport/routes`, `GET …/routes/{id}`) has `timings`: `leaves_at` (first pickup), `reaches_school_at` (estimated from the last stop's distance to school, never after school starts), `leaves_school_at` and `last_drop_at`, plus `problems` (number of stop time errors). School start and end come from the bell schedule. `GET /admin/transport/routes?flag=` takes `no_bus`, `inactive` or `has_problems`; `GET /admin/transport/routes/insights` gives `{ routes, active, stops, students, no_bus, with_problems }`.

**Stop time checks** on `PUT /admin/transport/routes/{id}/stops` (they block saving):

- Once one stop has a pickup (or drop) time, every stop needs one.
- Pickup times go up stop by stop, at least 2 minutes apart, and the last pickup is before school starts.
- Drop times go up from the last stop outwards (the evening order), at least 2 minutes apart, and the first drop is after school ends.
- A stop cannot lose the time its students need (a morning rider needs a pickup time, an evening rider a drop time).

Errors are `400 VALIDATION_FAILED` with `field` `items.N.pickup_time` or `items.N.drop_time` and a message naming the stop ("Pickup at Kilpauk (07:35) must be at least 2 minutes after Anna Nagar (07:40)"). Stops far apart but only minutes apart come back as a warning in `schedule_problems` on the route (`STOP_TIMES_TOO_CLOSE`), which does not block saving.

**No double booking.** A bus cannot run two routes at overlapping times (`409 BUS_TIME_CLASH`), and its driver or attendant cannot work another bus's route at the same time (`409 CREW_TIME_CLASH`). Checked when stops are saved, when a route gets a bus and when a route is switched on. A bus can run two rounds when they do not overlap. `RouteDetailDto.warnings` lists a missing bus, a bus off the road or not road-worthy, and a nearly full bus.

**Putting students on a stop** (`POST …/routes/{id}/stops/{stopId}/students`, `PUT /admin/students/{id}/transport`): only stops of that route; `400 ROUTE_HAS_NO_BUS`, `ROUTE_INACTIVE`, `STOP_TIME_MISSING` (no pickup time for morning riders or no drop time for evening riders); `409 BUS_FULL`. Giving a route another bus checks that bus's seats too.

**Change history and parent notes.** `GET /admin/transport/routes/{id}/history` lists what changed and when (`stop_time`, `stop_moved`, `stop_added`, `stop_removed`, `bus_changed`, `student_moved`, `pass_changed`) with `changed_by` and `parents_told`. Parents get an in-app note (`TRANSPORT_CHANGED`, no push, no SMS) when their child's stop time moves by 5 minutes or more, the stop moves 100 m or more, the child is moved to another stop, the route's bus changes, or the bus pass changes.

**Bus pass.** `PUT /admin/students/{id}/transport/pass` `{ "status": "on_hold" | "active", "note"? }`. The admin list (`GET /admin/transport/students?pass_status=on_hold`) shows `pass_status`, `pass_note`, `pass_changed_at`. The driver sees only `pass_status`, never fees or the note; the app shows "Bus pass on hold – contact office" and the child is never left behind. Parents see `pass_status` and `pass_note`.

**Parent app.** `GET /mobile/parent/children/{id}/transport` also returns `route_stops` (every stop in order with times, `is_my_stop`), `timings`, `pass_status`, `pass_note` and `recent_changes` (last 30 days, newest first, at most 10): route changes such as stop times plus this child's own changes ("Bus given on R1: boards at Kilpauk", "Moved to R2: …", "Pickup stop changed from A to B", "Evening stop changed from A to B").

**Driver app (Module 1).** `GET /mobile/driver/duty` returns `students`, `morning`, `evening`, `passes_on_hold`; each route has `path` ("Anna Nagar → Kilpauk → School"), `from`, `to`, `timings` and `students`; each student has `photo_url`, class and section, `parents` (name, relation, mobile, primary first), `mode`, `journey` ("Boards at Kilpauk 07:25 · Drops at Kilpauk 16:30") and `pass_status`. `GET /mobile/driver/students?search=&ride=morning|evening` is the same list for the whole bus, searchable by name, admission number or parent mobile.

**Driver app (Module 3).** `GET /mobile/driver/roster` returns the admin route roster for every active route on my bus: stops in route order, each with `pickup_students` (get on in the morning) and `drop_students` (get off in the evening), so a child with a different evening stop is listed at both. Each student has `pass_status`, `away_morning` and `away_evening`: null when the child rides that bus today, otherwise the reason to show ("On leave", "Half-day leave: comes in the afternoon", "Half-day leave: goes home at noon", "Sports OD – District athletics", "Marked absent"). Do not wait for an away child, but still let the attendant mark them if they turn up. Empty list when I have no bus. Use the roster before a trip starts (the plan) and `GET /mobile/driver/trips/{id}/checklist` while it runs (the live tick list). `GET /mobile/driver/duty` also has `away_morning` and `away_evening` counts, and every student in duty and `GET /mobile/driver/students` has `away_morning` / `away_evening`.

**Away rule (per bus).** Morning bus: approved full-day leave or morning half-day leave, sports OD for the whole day or the morning session, or marked absent / leave / OD in the morning attendance. Evening bus: the same with the afternoon half (afternoon attendance, or the morning mark when the afternoon is not taken yet). Late does not count. The same rule sets `status: away` and `away_note` in the trip checklist, trip riders and bus-history, and away children are never flagged `not_boarded`.

### Parent app

`GET /mobile/parent/children/{id}/bus` returns `status` (`no_trip`, `on_the_way`, `approaching`, `at_stop`, `passed`, `trip_ended`), a ready `headline` ("Bus is 4 min away from Thirumangalam metro"), the child's `stop`, `eta_seconds`, `position` (live, or the bus's last known position with `position_stale`), `trip` and `boarding` (the child's latest scan on that trip: `action`, `method`, `stop`, `occurred_at`; null before the first scan). It is `null` when the child does not use the bus.

**v2 with the stop timeline.** `GET /api/v2/mobile/parent/children/{id}/bus` is the same call with the same access rules; **v1 stays unchanged** and keeps working. v2 returns every v1 field plus:

| Field              | Meaning                                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `boarding_status`  | `not_yet`, `boarded` or `alighted` on today's trip                                                                                            |
| `last_position_at` | Time of the bus's last position, or `null`                                                                                                    |
| `timeline`         | `{ source, trip_id, kind, trip_date, child_stop_id, stops }`, or `null` when the route has no stops or no trip is planned in the next 14 days |

`timeline.source` is `live` while a trip runs (`trip_id` is that trip) and `scheduled` when none is running: then it is the next planned trip for the child's route and mode (today's pickup or drop if it has not run and its time has not passed, otherwise the next working day), `trip_id` is `null` and every stop is `pending`. Each item of `stops`, in travel order: `stop_id`, `name`, `sequence`, `planned_time` ("07:25"), `planned_at`, `status` (`pending`, `approaching`, `arrived`, `departed`, `skipped`), `eta_seconds` and `eta_at` (upcoming stops only, counted from the last bus position), `arrived_at` and `departed_at` (past stops only), `is_child_stop`, and `minutes_late` (minutes behind `planned_time`, negative when early: from the arrival for past stops, from the ETA for upcoming ones; `null` when unknown or skipped).

Parents are told automatically: **Bus has started** (whole route), **Bus is N min away** (only parents of that stop, before the bus arrives; SMS if the push does not reach the phone) and **Bus reached {stop}**, plus **{child} boarded the bus** and **{child} got off the bus** when the attendant scans the ID card.

At the end of a pickup, class teachers get the list of expected children who were not scanned on (only when the trip had at least one scan, so a bus without scanning sends no false list).

When a trip ends (by hand, from the office, or by itself) with children still marked on the bus, school admins and the transport in-charge get **{count} still on {bus} after the trip ended** with the names (push, SMS if the push does not reach the phone). It is sent once per trip.

At the same moment the parents of each child who was expected on that trip (not away) and never marked get **{student} did not come on the morning bus / evening bus** (`CHILD_NOT_ON_BUS`, push and in-app, data `student`, `bus`, `trip`, `trip_id`, `student_id`). It is skipped when the attendant marked nobody on the trip, so a trip run without the app does not alarm every parent.

### Live updates (socket.io)

Connect to the namespace `/live` on the API host with `{ auth: { token: "<access_token>" } }`, then:

- `emit('trip.subscribe', { trip_id })` → ack `{ ok: true }`. A parent can follow only a trip their child rides; a driver only their own bus; admins any trip of their school. Otherwise `{ ok: false, error: "FORBIDDEN" }`.
- Receive `trip.position` `{ trip_id, position: { lat, lng, speed, heading, recorded_at, source } }` every few seconds and `trip.event` `{ trip_id, type, stop, eta_seconds, end_reason }` for `trip.started`, `stop.approaching`, `stop.arrived`, `stop.departed`, `trip.ended`.
- `passenger.boarded` / `passenger.alighted` `{ trip_id, boarding_id, student_id, action, method, stop, occurred_at }` on each scan. The fleet room (admin web) also gets `full_name` and `class_section`; trip followers (parents) get only `student_id`.
- `passenger.undone` `{ trip_id, route_id, vehicle_id, boarding_id, student_id, action }` when the attendant undoes a wrong tap: drop that mark.
- Admin web: `emit('fleet.subscribe', {})` to get every trip of the school plus `alert.raised` and `alert.updated` (same shape as an alerts centre row).
- When the access token expires the socket is closed with an `error` event: refresh the token and connect again.

**SOS screen in the driver app.** Show the SOS button on the trip screen while a trip runs, and also on the home screen. Trigger it with a 3-second long press or a confirm dialog, never a single tap. Send the phone's `lat`/`lng` with the press. If the request fails, retry until it gets through; a repeat within 2 minutes is safe. Then show a full-screen status: "Sent, waiting for the office" (`open`) or "{acknowledged_by.name} has seen it" (`acknowledged`). Keep sending the location every 15 s, offer **Cancel (false alarm)**, and close the screen when `sos/active` returns `null`. The crew also get the push `SOS_ACKNOWLEDGED` / `SOS_RESOLVED` (category `alert`, `alert_id` in data) and the `/comm` socket event `sos.updated` with the alert. Teachers receive `SOS_ALERT`, `SOS_RESOLVED` and `SOS_CANCELLED` as read-only alert cards in the staff app.

### Alerts centre (admin web)

`GET /admin/fleet/alerts` lists SOS and safety alerts, newest first: search (message, bus, driver), `kind` (`sos`, `overspeed`, `harsh_braking`, `idle`, `route_deviation`, `vehicle_fault`, `other`), `status` (`open`, `acknowledged`, `resolved`), `severity`, `active=true` (not resolved), `vehicle_id`, `trip_id`, `from`, `to`. Each row has `kind_label`, `message`, `vehicle`, `route`, `trip`, `raised_by` (with `mobile` to call), `position`, `data` and who acknowledged or resolved it. `GET /admin/fleet/alerts/insights` returns `open`, `sos_active`, `high_active`, `acknowledged`, `resolved_today`, `raised_today` and `active_by_kind`. `GET /admin/fleet/alerts/{id}` returns one alert. `POST .../{id}/acknowledge` (safe to repeat) and `POST .../{id}/resolve` `{ "resolution_note": "Called the driver, all safe" }` (at least 3 characters) need `fleet.manage`; reading needs `fleet.view`. Acknowledging or resolving an SOS tells the driver and attendant (push and `sos.updated`), and resolving also tells the teachers. Statuses read as Raised (`open`), Acknowledged and Resolved; a crew cancel has `data.cancelled: true`.

Safety alerts come from the Telematics service as `alert.raised` webhook events (overspeed, harsh braking, idling, off route). The bus is found from `device_id` (and the trip, when given). Retries of the same event are stored once. The office gets a push; `high` severity also an SMS when the push does not reach the phone.

## Gate passes and visitors

New role **Gate in-charge** (`GATE_INCHARGE`, Staff app; demo 9000000009). Permissions: `gate.view` (see), `gate.operate` (work the gate), `gate.approve` (teachers for their own class, principal, AO, admin), `gate.manage` (office: invite, cancel, blocked list, pickups, settings).

**A gate pass can be checked three ways**, all against the server: scan the **QR** (`qr_token`, signed `TZG1.p.<id>.<version>.<sig>`), type the **4-digit code**, or type the **pass number** (`GP-2026-0042`). Without any of them the gate finds the student (**manual**) and must take a photo of the person and note the ID proof (last 4 only). Green needs: approved, for today, inside `from_time`–`until_time` with `grace_minutes`, not used, parent code entered when needed, student not marked absent. Red verdicts: `not_approved`, `rejected`, `cancelled`, `used`, `expired`, `not_today`, `too_early`, `consent_needed`, `student_absent`, `not_found`. 5 wrong codes in 10 minutes lock code entry for that user (429 `TOO_MANY_TRIES`). Only the parent and the office see `qr_token` and `code`; the gate never does. Releasing before the afternoon attendance adds an approved afternoon half-day leave (attendance and the evening bus show the child away). Both parents get `GATE_RELEASED`; a manual release also tells the office (`GATE_MANUAL_RELEASE`, setting `notify_office_on_manual`).

**Emergency without a pass** (`POST /mobile/teacher/gate/emergency`): for a registered parent (`can_pickup`) or a saved pickup person the class teacher and the office get `GATE_EMERGENCY` and the first answer wins (`PASS_ALREADY_DECIDED`). For anyone else (`pickup.kind = other`, photo required) the parents also get `GATE_CONSENT_NEEDED`; the office cannot approve until a parent agrees (409 `CONSENT_PENDING`); the parent's app then shows a code the parent reads out, and the gate enters it (`POST .../consent-code`) before release. Someone on the blocked list gets 403 `PERSON_BLOCKED` and the office `GATE_BLOCKED_PERSON`. Unanswered after `emergency_wait_minutes` → the gate gets `GATE_NO_ANSWER` (call the office).

**Visitors**: walk-in (photo required by default) waits for the staff member being met (or the office) → `allowed` → in → out; invited visitors get an SMS with a slip number (`VP-2026-0009`) and a 4-digit code and go straight in. Visitors past `expected_until` give the office `VISITOR_OVERSTAY`; anyone still inside at `visitor_checkout_time` is checked out (`check_out_method: auto`).

## AO office: wings

A school is split into **wings** (for example Pre-primary LKG–UKG, Primary 1–5, Secondary 6–10, Higher Secondary 11–12). A wing is a grade range (`-1` LKG, `0` UKG, `1` to `12`) or an exact list of classes (`class_ids`, for a school with two boards). A class can be in one wing only (`409 WING_OVERLAP`).

- **Wing AO**: an AO with one or more wings. Everything tied to a class is limited to their wings: student list, every `/admin/students/{id}/…` route, gate passes, the office drill-down. A student outside their wings is `404 STUDENT_NOT_FOUND`.
- **Head AO**: an AO with no wing today. Sees the whole school and the **AO monitor**.
- Cover during leave: an AO's wing can have `valid_from` / `valid_to`; it counts only between those dates.
- Admin and principal are never limited. Permissions: `office.view` (drill-down, student history), `office.wings` (wing setup: admin, principal), `office.monitor` (AO monitor: head AO, principal, admin).

**Kinds.** `kind=extra`: only `student_ids` (for example below-average or average students). `kind=special`: the whole section, including students who join later; only for classes turned on in the settings (`400 CLASS_NOT_ALLOWED`).

**Timing.** `timing=period`: one bell-schedule period every week (`day_of_week`, `period_no`); the students miss that period and it counts toward the teacher's weekly limit. `timing=extra_time`: its own `start_time` and `end_time` on the chosen `days` (0 = Sunday … 6 = Saturday) between `start_date` and `end_date` (no days = that one date). It may be before or after school, in a break or lunch, or on a Sunday or holiday (`day_part` full / morning / afternoon / custom is a label for people); it does not count toward the weekly limit. `when` is a ready line such as "every Mon, Wed, 4:00 PM – 5:00 PM, 1 Dec to 28 Feb".

**Checks.** `409 DURING_CLASS_TIME` (extra time overlaps a teaching period on a school day), `TEACHER_CLASH` (the teacher has another class, regular or special, then), `STUDENT_CLASH`, `SPECIAL_CLASS_CLASH` (two period classes in one section), `TEACHER_OVER_LIMIT` (period classes only).

**Notifications.** Created: the teacher gets `SPECIAL_CLASS_ASSIGNED`, parents `SPECIAL_CLASS_ADDED`. Changed time or title: `SPECIAL_CLASS_CHANGED`; new students' parents get `ADDED`, removed students' parents and a replaced teacher get `SPECIAL_CLASS_CANCELLED`. Stopped: everyone gets `SPECIAL_CLASS_CANCELLED`. Absent in the class today: parents get `SPECIAL_CLASS_ABSENT`.

**Class-wise holidays.** `POST/PATCH /admin/holidays` take `class_ids` (null = whole school); each holiday returns `whole_school` and `classes`. ## Exams, marks and ranking

Grades (CBSE-like, on the percentage): A1 91+, A2 81+, B1 71+, B2 61+, C1 51+, C2 41+, D 33+, E below. A student fails with any subject below its pass marks or absent. `percent` has one decimal. - `columns[]`: one per exam in order, with `total`, `max_total`, `percent`, `grade`, `result`, `section_rank`/`section_size`, `class_rank`/`class_size`, and `common_max` (the max marks when every paper has the same, for the header "Quarterly exam (100)").
- `subjects[]`: languages first, then theory, practical and activity, each by name. `cells[]` has one entry per column (`null` when the subject was not in that exam; `passed: null` when marks are not entered). The row's `total`, `max_total`, `percent`, `grade` add up every exam; `passed` is false when the total is below the sum of the pass marks.
- `overall`: totals of the complete exams. `result` is `fail` only when a subject's combined total is below its combined pass marks, so one weak unit test does not fail the year.
- `attendance`: daily attendance (period 0) in `scope.from`–`scope.to` (term or year dates, never after today). `late` counts as present, `half_day` as half.
- `remarks` (from the overall percentage), `grade_scale`, `options` (`academic_years`, `terms`, `exams` for the pickers) and `pdf_path`.

Errors: `404 STUDENT_NOT_FOUND`, `ENROLLMENT_NOT_FOUND`, `TERM_NOT_FOUND`, `EXAM_NOT_FOUND`, `SECTION_NOT_FOUND`, `CHILD_NOT_FOUND`; the PDFs give `404 NO_PUBLISHED_RESULTS` when there is nothing to print.

**Recording a payment safely.** Send an `Idempotency-Key` header (8 to 80 letters, digits, `_ . : -`; a UUID made when the payment form opens) with `POST /admin/fees/invoices/{id}/payments`. If the same request is sent again (double click, retry after a timeout), the API returns the first payment instead of recording a second one. The same key with another invoice or amount is refused with `409 IDEMPOTENCY_CONFLICT`. The header is optional, but without it a repeated request records the payment twice.

**Approval of discounts, cancellations, reversals and refunds.** These four routes no longer change anything directly. Each one validates the change, then creates a pending request and answers **202** with the request:

- `PATCH .../discount` `{ discount, reason }`: `reason` is now required.
- `POST .../cancel` `{ reason }`: `reason` is now required.
- `POST /admin/fees/payments/{id}/reverse` `{ reason }`.
- `POST /admin/fees/invoices/{id}/refunds` `{ amount, mode, reference?, paid_on?, reason }`.
- `POST /admin/fees/invoices/{id}/reschedule` `{ due_date, reason }` moves the due date. The new date must be inside the invoice's year, and the invoice must still have a balance (409 `INVOICE_PAID`). On approval, `original_due_date` keeps the first date and overdue reminders start again from the new one.

The invoice changes only when someone with `fees.approve` approves:

- `POST /admin/fees/requests/{id}/approve` `{ comment? }` checks the change again and applies it in the same transaction.
- `POST /admin/fees/requests/{id}/reject` `{ comment }`.
- The person who asked cannot approve it (403 `SELF_APPROVAL`). With only an AO and the School Admin, one approves the other's requests.
- The person who asked can `POST .../withdraw` (403 `NOT_REQUESTER` for anyone else).
- Only one request of a kind can wait per invoice, or per payment for a reversal (409 `REQUEST_PENDING`). A decided request returns 409 `REQUEST_NOT_PENDING`.
- `GET /admin/fees/requests` filters by `status`, `kind`, `invoice_id` and `student_id`; `search` matches the student, invoice number and reason.
- Each request has `kind` (`discount`, `cancel`, `reversal`, `refund`, `reschedule`, `write_off`), `status` (`pending`, `approved`, `rejected`, `withdrawn`), `invoice`, `payment`, `student`, `amount`, `details`, `reason`, `requested_by`/`requested_at` and `decided_by`/`decided_at`/`decision_comment`.
- The invoice detail adds `pending_requests[]` (with `details`), so screens can show what is waiting.
- The parent fee summary (`GET /mobile/parent/children/{id}/fees`) leaves out `pending_requests` and payment `notes`; both are for school staff.

**One payment across invoices and advance credit.** `POST /admin/fees/students/{id}/payments` `{ amount, mode, reference?, paid_on?, notes? }` needs `fees.collect`. Send an `Idempotency-Key` header; a retry returns the first result with `replayed: true`.

- It pays the student's unpaid invoices oldest due date first. Earlier years are included; archived years are left out. Each invoice gets its own payment and receipt, linked by `collection_id`.
- Anything left over is kept as **advance credit**, with its own receipt number (`advance_receipt_no`).
- The answer is `{ collection_id, amount, applied_amount, advance_amount, advance_receipt_no, credit_balance, replayed, payments[] }`.
- Credit is used automatically when invoices are raised (`POST /admin/fees/invoices/generate`). `POST /admin/fees/students/{id}/apply-credit` uses it on unpaid invoices now. Credit used this way is a payment with `mode: "credit"`.
- Reversing a credit payment returns the amount to the credit.
- `mode` on every payment input is `cash`, `upi`, `card`, `bank_transfer` or `cheque`. Payments can also show `online` (Razorpay) and `credit`.
- Money-received figures (today's collection, `/payments/summary`, the collection report) leave out `credit` payments, because that money was already counted as advance when it came in. `GET /admin/fees/insights` adds `todays_advance`. The collection report has an Advance column.
- The student fee summary (admin and parent) adds `credit_balance` and `advances[]` (`{ collection_id, receipt_no, amount, collected, mode, paid_on }`, newest first): one entry per payment that had a part kept as advance.
- Advance receipt PDF: `GET /admin/fees/collections/{collection_id}/advance-receipt` (`fees.view`) and `GET /mobile/parent/children/{id}/fees/advance-receipts/{collection_id}`. It shows the amount paid, the part paid towards each invoice (those have their own receipts) and the part kept as advance. 404 `RECEIPT_NOT_FOUND` when the payment had no advance.

**Leaving the school: NOC before the TC.** A TC is issued only after a no-objection clearance (NOC) from every department.

- `POST /admin/students/{id}/noc` `{ exit_type: transferred|withdrawn, leaving_date, reason }` (`students.manage`) starts a leaving request with five lines: `fees`, `library`, `transport`, `inventory`, `class_teacher`. The student stays `active`. `409 NOC_EXISTS` when one is already open, `409 STUDENT_NOT_ACTIVE` when the student has left.
- `GET /admin/students/{id}/noc` returns `{ id, student_id, status: open|cleared, exit_type, leaving_date, reason, requested_by_name, requested_at, cleared_at, cleared_count, items[] }`. Each item has `department`, `status: pending|cleared`, `blocker` (what is outstanding right now, e.g. "2 library books not returned", "Rs. 4,500.00 of fees unpaid", "On route R1, stop Anna Nagar"), `blocking` (true when it cannot be cleared yet), `amount` (unpaid fees, fees line only), `can_clear` for the signed-in user, `cleared_by_name`, `cleared_at`, `remarks`, `blocker_snapshot`. `404 NOC_NOT_FOUND` when no request is open.
- `POST /admin/students/{id}/noc/items/{department}/clear` `{ remarks?, acknowledge_dues? }`. `students.manage` clears any line; otherwise fees needs `fees.manage` or `fees.approve`, library `library.manage`, transport `fleet.manage`, inventory `inventory.manage` (`403 NOC_FORBIDDEN`). Fees answers `409 FEE_DUES_PENDING` while fees are unpaid unless `acknowledge_dues: true`. Library answers `409 LIBRARY_CLEARANCE_PENDING` while books are out or fines unpaid. Clearing transport takes the student off their bus. When the last line clears, the NOC becomes `cleared`.
- `POST .../noc/items/{department}/reopen` undoes a clearance until the TC is issued. `POST .../noc/cancel` `{ note }` (`students.manage`) cancels the request; the student stays.
- `GET .../noc/pdf` prints the NOC with every line.
- `GET /admin/students/{id}` returns `noc_status: open|cleared|null`.
- `POST /admin/students/{id}/exit` now needs a cleared NOC (`409 NOC_NOT_CLEARED`). `exit_type`, `leaving_date` and `reason` are optional and default to the NOC. On success the NOC becomes `issued`. The TC PDF prints the EMIS number.

**Transfer certificate with dues.** `POST /admin/students/{id}/exit` answers 409 `FEE_DUES_PENDING` (the message gives the amount) when the student has unpaid fees and the fees line of the NOC was cleared without acknowledging them. Send `acknowledge_dues: true` to issue the TC anyway. The dues stay on record, and the TC stores `fee_balance`. To stop collecting them, ask for a write-off: `POST /admin/fees/invoices/{id}/write-off` `{ reason }` (needs approval, kind `write_off`). On approval the balance is added to the discount as "Written off: <reason>" and the invoice becomes paid.

**Online payment (Razorpay).** It is switched off until `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` are set (otherwise 503 `ONLINE_PAYMENTS_OFF`).

1. The parent app calls `POST /mobile/parent/children/{id}/fees/invoices/{invoiceId}/pay-online` `{ amount? }`. The amount defaults to the balance and cannot be more. It returns `{ gateway, key_id, order_id, amount_paise, amount, currency, name, description, prefill }` for the Razorpay checkout.
2. After the checkout succeeds, the app sends `razorpay_order_id`, `razorpay_payment_id` and `razorpay_signature` to `POST /mobile/parent/children/{id}/fees/online-payments/verify`.
3. The API checks the signature (400 `INVALID_PAYMENT_SIGNATURE`) and records the payment as a collection with `mode: "online"`. The paid invoice comes first; anything over becomes credit.

Also set up the webhook `POST /api/v1/integrations/razorpay/webhook`:

- Add it in Razorpay Dashboard → Webhooks with the events `payment.captured`, `order.paid` and `payment.failed`, and the secret `RAZORPAY_WEBHOOK_SECRET`.
- It records payments the app could not confirm.
- A payment is recorded only once, whichever arrives first.

`GET /admin/fees/online-payments` lists orders (`status`: `created`, `paid`, `failed`).

**Previous dues.** `GET /mobile/parent/children/{id}/fees` and `GET /admin/students/{id}/fees` add `previous_dues: { amount, invoices, academic_years }`. This is the unpaid balance of invoices from academic years before the current one. It is already part of `balance`; it is shown apart so parents can see what is left from earlier years.

**Reversing a payment.** A reversal (after approval) is for a bounced cheque or a payment entered by mistake. The payment is never deleted: it keeps its receipt number and gets `status: "reversed"`, `reversed_at`, `reversed_by` and `reversal_reason`, and the invoice's `paid`, `balance` and `status` go back. Reversing twice returns `409 PAYMENT_ALREADY_REVERSED`. Its receipt PDF is marked REVERSED.

Every payment in every response (admin and parent) now carries `status` (`success` or `reversed`) and the three reversal fields. Reversed payments are still listed in payment history, but they never count as paid: they are left out of invoice and student totals, `last_payment`, `/payments/summary`, today's collection and the dashboard. `GET /admin/fees/payments?status=success|reversed` filters the list.

**Fee head details.** Besides `name`, `code`, `is_transport` and `is_active`, a head has `description`, `fee_group` (free text such as Academic or Activities), `is_mandatory` (default `true`; `false` marks an optional fee such as sports or uniform), `frequency` (`one_time`, `monthly`, `quarterly`, `half_yearly`, `yearly`, `per_term`, `custom`; default `custom`; for display and reports, the plan still sets the installments), `is_refundable` (default `false`) and `applicable_class_ids` (empty = every class). `GET /admin/fees/heads` filters by `is_mandatory`, `frequency` and `fee_group`. A head limited to some classes cannot go on another class's plan (400 on `lines.N.fee_head_id`), and its classes cannot be narrowed while a plan of the current or a draft year for a left-out class uses it (400 on `applicable_class_ids`).

**Fee plan approval.** A class's fee plan changes only through an approved version, and only the version in use (`fee_plans`) is used for invoices.

- `PUT /admin/fees/plans/{classId}` now saves a **draft**. The first save creates version n+1; later saves replace the same draft. It no longer changes the plan in use. While a version is waiting for approval it returns 409 `PLAN_PENDING_APPROVAL`.
- `POST .../submit` `{ note? }` sends the draft for approval.
- `POST .../approve` `{ comment? }` makes it the plan in use. The previous version becomes `superseded`. The person who sent it cannot approve it (403 `SELF_APPROVAL`).
- `POST .../reject` `{ comment }` (at least 3 characters) sends it back as a draft, with the comment.
- `DELETE .../draft` throws the draft away.
- With nothing waiting, approve and reject return 409 `PLAN_NOT_PENDING`. With no draft, submit and discard return 404 `PLAN_DRAFT_NOT_FOUND`.
- `GET /admin/fees/plans/{classId}` adds `version` (the version in use, `null` if none) and `draft` (the open version, or `null`). Each version has `id`, `version`, `status` (`draft`, `pending_approval`, `published`, `superseded`), `lines` (with `head_name`), `installments`, `total`, `note`, `created_by`, `submitted_by`/`submitted_at`, `reviewed_by`/`reviewed_at`, `review_comment` and `published_at`. The `_by` fields are `{ id, name }`.
- `GET /admin/fees/plans` adds `version` and `draft_status` (`draft`, `pending_approval` or `null`) for each class.
- `GET /admin/fees/plans/{classId}/versions` lists every version, newest first.
- These routes accept `?academic_year_id=` and default to the current year.
- The upgrade marks each class's existing plan as version 1, in use.
- Invoices already raised never change.

**Copying plans.** Both routes make drafts only. Plans in use never change until a draft is approved. They need `fees.configure`.

- `POST /admin/fees/plans/{classId}/copy` `{ to_class_ids, academic_year_id? }` copies a class's plan in use to other classes of the same year.
- `POST /admin/fees/plans/copy-year` `{ from_academic_year_id, to_academic_year_id?, class_ids? }` copies every plan in use from an earlier year. The target defaults to the current year. Due dates move by the difference in years (29 February becomes 28 February) and are kept inside the target year.
- Both return `{ drafted, skipped, classes: [{ class_id, class_name, status: 'drafted' | 'skipped', version, lines, left_out, reason }] }`.
- Heads that are switched off, transport, or not for the target class are left out (`left_out`).
- A class that already has a draft or a change waiting is skipped with a `reason`.
- Nothing to copy returns 409 `PLAN_EMPTY`. Copying a year onto itself returns 400.

**Reports.** `GET /admin/fees/reports/{type}` (`fees.view`) returns `{ title, academic_year, note, from, to, columns: [{ key, label, kind }], rows, totals }`. `kind` is `text`, `money`, `number`, `percent` or `date`, and each row is an object keyed by the column keys. `GET /admin/fees/reports/{type}/xlsx` downloads the same report as Excel.

Every report takes `academic_year_id`, `class_id`, `section_id` and `installment`, and leaves out cancelled invoices. `collections` and `collectors` also take `received_by` (a staff user id): fees and library fines by who received them, advances and refunds by who recorded them.

| `type`         | Rows                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `classes`      | Per class: students, invoices, billed, concessions and scholarships, discounts, net due, collected, outstanding, overdue, collected %                                                                                                                                                                                                                                                                      |
| `heads`        | The same per fee head (`fee_head_id` filters). An invoice's discount and payments are shared across its heads by amount                                                                                                                                                                                                                                                                                    |
| `installments` | The same per installment, with the due date and how many invoices are fully paid                                                                                                                                                                                                                                                                                                                           |
| `benefits`     | Each concession and scholarship: students who have it, students billed with it, invoices, amount taken off (`kind` filters)                                                                                                                                                                                                                                                                                |
| `defaulters`   | Students with a balance: net due, paid, balance, overdue, oldest due date, days overdue, most overdue first (`overdue_only=true`)                                                                                                                                                                                                                                                                          |
| `collections`  | Money received per day between `from` and `to` (default: this month): receipts, one column per mode (`cash`, `upi`, `card`, `bank_transfer`, `cheque`, `online`), `fees`, `advance`, `library_fines`, `refunds` (paid out), `net` and `cash_in_hand` (cash received less cash refunded). Reversed payments are left out. Library fines are left out when `class_id`, `section_id` or `installment` is sent |
| `collectors`   | The same totals per staff member who received the money (`collector`); online payments are one row, `Online (parent app)`                                                                                                                                                                                                                                                                                  |

**Daily collection.**

- `GET /admin/fees/reports/collector-options` (`fees.view`) lists `{ id, name }` of everyone who has received fees, advances or library fines, or paid out a refund, for a "received by" filter.
- `GET /admin/fees/payments` and `GET /admin/fees/payments/summary` also take `received_by`.
- `GET /admin/fees/reports/day-sheet?date=&received_by=` (`fees.view`) is the day-end collection sheet PDF: every fee receipt, advance receipt, library fine receipt and refund paid out on `date` (default today), a table of received, refunded and net by payment mode, cash in hand to deposit, and signature lines. `received_by` limits it to one person's counter.

**Concessions and scholarships.** Both use the same routes. `kind` is `concession` or `scholarship`, and they belong to an academic year.

- `GET /admin/fees/benefits` filters by `kind`, `type`, `is_active` and `academic_year_id`; `search` matches the name and description; sort by `name`, `value` or `created_at`. `GET`/`PATCH`/`DELETE /admin/fees/benefits/{id}`, `POST /admin/fees/benefits`.
- Fields:
  - `name`: unique per year and kind, otherwise 409 `BENEFIT_EXISTS`.
  - `type` for a concession: `sibling`, `staff_child`, `merit`, `sports`, `financial`, `management` or `other`.
  - `type` for a scholarship (who funds it): `government`, `institution`, `trust`, `private` or `other`.
  - `calc_type` is `percent` (`value` up to 100) or `fixed` (`value` is rupees a year).
  - `fee_head_ids`: empty means every head except transport.
  - `class_ids`: empty means every class.
  - `description` and `is_active`.
- Responses add `active_awards` and `amount_given` (taken off invoices that are not cancelled).
- One that was ever given cannot be deleted (409 `BENEFIT_IN_USE`). Switch it off instead.
- `POST /admin/fees/benefit-awards` `{ benefit_id, student_ids, reason }` gives it to students.
  - Each student must be studying that year, in a class it is open to. Otherwise 400 on `student_ids.N`.
  - Students who already have it are skipped (`already_awarded`).
  - A switched-off one returns 409 `BENEFIT_INACTIVE`.
- `POST /admin/fees/benefit-awards/{id}/revoke` `{ reason }` withdraws it. Doing it twice returns 409 `AWARD_REVOKED`.
- `GET /admin/fees/benefit-awards` filters by `benefit_id`, `kind`, `student_id`, `status` (`active`, `revoked`) and `academic_year_id`; `search` matches the student name, admission number and the concession or scholarship name.
- Writes in a closed or archived year return 409 `YEAR_CLOSED`.
- Scholarships are managed only in the admin web. Parents do not apply in the app.

How they are applied when invoices are raised:

1. Concessions first, then scholarships, each in the order they were created.
2. A percentage is taken from the fee head's amount on the invoice, never compounded.
3. A fixed amount is a yearly figure, spread over the plan's installments in proportion to the eligible amount of each. The last installment takes the rounding remainder, so the year adds up exactly.
4. The total taken off a line never goes above the line, so no fee goes below 0.
5. Amounts are rounded to the paisa.

Giving, withdrawing or changing one affects only invoices raised afterwards.

- Invoices add `benefit` (the total taken off), so `total = gross − benefit − discount`. The invoice detail adds `benefits[]`: `benefit_id`, `kind`, `name`, `fee_head_id` and `amount`.
- A manual discount can be at most `gross − benefit − paid`.
- An invoice whose total comes to 0 is raised as `paid`, and no due notice is sent for it.
- `POST /admin/fees/invoices/generate` adds `with_benefits` and `benefit_amount`.
- Receipt PDFs show a "Concessions and scholarships" line.
- The parent and teacher fee screens are unchanged. They already show `total`, which is net of these.

**Audit log.** `GET /admin/fees/audit-logs` lists every change to fee heads, plans, invoices and payments, newest first. Each row has `entity` (`fee_head`, `fee_plan`, `fee_invoice`, `fee_payment`, `invoice_run`, `fee_benefit`, `benefit_award`), `entity_id` (the class id for `fee_plan`, `null` for an invoice run), `action` (`created`, `updated`, `deleted`, `replaced`, `generated`, `discounted`, `cancelled`, `paid`, `reversed`, `submitted`, `approved`, `rejected`, `discarded`, `awarded`, `revoked`), the values `before` and `after`, `reason`, `user` and `created_at`. Filters: `entity`, `entity_id`, `action`, `user_id`, `from`, `to`; `search` matches the reason and the user's name. Each row is written in the same transaction as the change it records.

**Balance check.** `GET /admin/fees/reconciliation` returns `invoices_checked` and `mismatches`: invoices whose `paid` differs from the sum of their non-reversed payments, or whose `total` or `balance` does not add up. It only reads; nothing is fixed automatically. The same check runs every night at 02:30 and logs a warning for each school with mismatches.

The database also refuses negative amounts, payments of 0, and invoices whose totals do not add up (`CHECK` constraints, enforced on new and changed rows).

## Accounts: expenses and other income (admin web)

School expenses (electricity, stationery, repairs, rent…) and money received other than fees (donations, uniform and book sales, hall rent…). Bus fuel and bus expenses stay in Maintenance and salaries in Payroll; the reports below bring them in.

Permissions:

- `accounts.view`: school admin, Principal, AO, Accountant.
- `accounts.manage` (add and edit entries): school admin, AO, Accountant.
- `accounts.approve` (approve, reject, void; manage categories): school admin, Principal, AO.

**Categories.** `GET /admin/accounts/categories?kind=expense|income&include_inactive=true` returns `{ id, kind, name, is_active, entries }`. A school gets a standard list the first time it is read. `POST /admin/accounts/categories` `{ kind, name }` (409 `CATEGORY_EXISTS`, names are compared without case), `PATCH /admin/accounts/categories/{id}` `{ name?, is_active? }`, `DELETE /admin/accounts/categories/{id}`: only an unused one, otherwise 409 `CATEGORY_IN_USE` (switch it off instead).

**Entries.** `/admin/accounts/entries`:

- `GET` lists them, newest first. Filters: `kind`, `status`, `category_id`, `payment_mode`, `from`, `to`. `search` matches the entry no., party, reference, note and category. Sort: `entry_date`, `amount`, `created_at`, `entry_no`.
- `GET /insights`: `income_this_month`, `expense_this_month` (approved only), `pending`, `pending_amount`, `pending_expense`, `pending_income`, `expense_by_category`, `income_by_category`.
- `POST` `{ kind, category_id, entry_date, amount, payment_mode?, party?, reference?, file_id?, note? }`:
  - `payment_mode` is `cash` (default), `upi`, `card`, `bank_transfer` or `cheque`.
  - `party` is who was paid (expense) or who paid (income); `reference` is the bill, cheque or UTR number; `file_id` is an uploaded bill (purpose `account_bill`).
  - `entry_date` cannot be in the future. The category must be of the same kind and switched on.
  - The server gives `entry_no` (`TZMS-EXP-2026-0001`, `TZMS-INC-2026-0001`).
  - With `accounts.approve` the entry is `approved` at once; otherwise it is `pending` and not counted anywhere until approved.
- Each entry has `status` (`pending`, `approved`, `rejected`, `void`), `created_by`, `decided_by`, `decided_at`, `decision_note` (the reject note or void reason) and `can_edit` (the caller may edit or delete it now).
- `PATCH /{id}`: only while `pending`, by who added it or an approver. 409 `ENTRY_LOCKED` once decided, 403 `NOT_ENTRY_OWNER`.
- `DELETE /{id}`: a `pending` or `rejected` entry, by who added it or an approver. An approved one returns 409 `ENTRY_LOCKED`.
- `POST /{id}/approve` and `POST /{id}/reject` `{ note? }`: a pending entry only, otherwise 409 `ENTRY_ALREADY_DECIDED`.
- `POST /{id}/void` `{ reason }`: an approved entry only (409 `ENTRY_NOT_APPROVED`). It stays on record as `void` and leaves the reports. To correct an amount, void it and add a new entry.
- `GET /{id}/voucher`: payment voucher (expense) or income receipt PDF, with the amount in words and the approval status.

**Reports.** `GET /admin/accounts/reports/{type}` (`accounts.view`) returns the same shape as the fee reports; `/xlsx` downloads it. `from` and `to` default to the academic year start and today.

| `type`       | Rows                                                                                                                                                                                                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `monthly`    | Per month: `fees` (received with advances, less refunds), `library_fines`, `other_income`, `total_income`, `school_expenses`, `bus_costs` (approved fuel and bus expenses), `salaries` (net pay of finalised payroll runs, by payroll month), `total_expense`, `net` |
| `categories` | `section` (Income or Expense), `category`, `amount`, `share` (% of income or of expense). `totals` is the surplus                                                                                                                                                    |
| `register`   | Every approved entry: date, entry no., type, category, party, mode, reference, added by, income, expense (`kind` filters)                                                                                                                                            |

Only approved entries are counted. The `salaries` column and row appear only for callers with `payroll.view`.

## Library

The librarian (role `LIBRARIAN`, admin web) runs the catalogue, the issue desk, overdue follow-ups, fines, library attendance and stock checks. Permissions: `library.view` (Librarian, Principal, AO, school admin), `library.manage` (catalogue, members, issue and return, stock checks, settings), `library.fines` (collect; Librarian, AO), `library.waive` and `library.attendance` (door scan, library periods). Every route below is under `/admin/library` unless shown otherwise.

**Barcodes.** A book (title) has an `isbn`; each physical copy has its own `accession_no` (`TZMS-000123`, from the school sequence or the school's own register) and `barcode` (a barcode already on the book, else the accession number). Scanners type the code and Enter, so every scan field is a plain text input. `GET books/isbn/{isbn}` takes the EAN-13 on the back cover (or ISBN-10) and returns `book` (already here: add copies) or `suggestion` (details from the online lookup when `BOOK_LOOKUP_URL` is set and the library setting `isbn_lookup` is on). `GET copies/lookup?code=` finds a copy by barcode or accession number; `GET copies/labels?copy_ids=|book_id=|added_from=` prints A4 sheets of Code 128 stickers (3 × 8).

**Catalogue.** `categories` (CRUD; `is_reference` books are never issued), `books` (search title, author, ISBN, publisher, keywords, accession, barcode; `category_id`, `language`, `availability`, `is_active`; sort `title`, `authors`, `created_at`, `available`), `books/insights`, `POST books` with optional `copies` `{ count, barcodes[], accession_nos[], condition, source, vendor, bill_no, acquired_on, price }`, `books/{id}/copies` (`GET`, `POST`), `copies` (inventory list), `PATCH copies/{id}` (barcode, condition, shelf status `available`, `damaged`, `in_repair`, `withdrawn`), `copies/{id}/history` (every event: added, issued, returned, renewed, marked lost, found, damaged, repaired, withdrawn, audited). Import: `GET books/import/template` (xlsx) then `POST books/import` multipart `file` + `mode=validate|import`; a known ISBN adds copies, barcodes and accession numbers are separated by `|`, unknown categories are created.

**Members.** Students and staff are mapped to a library card (`TZMS-LS-00007` student, `TZMS-LT-00003` staff). `GET members/lookup?code=` accepts the card number, the ID card QR (`TZS1…`, an old replaced card gets `409 QR_REPLACED`), admission number, employee number or staff mobile, and enrols a non-member on the spot (`enrolled_now`). It returns the member, books held, unpaid fines, `books_left`, `can_borrow` and `refusal`. Also `members` (list), `members/insights`, `members/people?search=` (desk search), `POST members`, `POST members/bulk` `{ section_id | class_id | all_students | all_staff }`, `PATCH members/{id}` (suspend, own `max_books`, `loan_days`). `phone` on a member is the first parent's mobile for a student, the staff member's own mobile for staff.

**Issue and return.** `POST issues` `{ member_id, codes[], due_date?, purpose: personal | class_set, section_id?, remarks? }` is all or nothing; refusals: `COPY_NOT_FOUND`, `COPY_NOT_AVAILABLE`, `REFERENCE_ONLY`, `SAME_TITLE_HELD`, `BOOK_LIMIT_REACHED`, `FINE_PENDING`, `MEMBER_NOT_ACTIVE`, `MEMBER_LEFT`. A class set goes to a teacher for a section and ignores the book limit. The due date is the loan days (14 students, 30 staff by default) moved off Sundays and holidays. `POST returns` `{ items: [{ code, condition?, damage_fine?, remarks? }] }` (`NOT_ON_LOAN`). `POST issues/{id}/renew` (`RENEW_LIMIT_REACHED`, `LOAN_OVERDUE`; adds the loan days to the later of today and the current due date), `POST issues/{id}/lost`, `POST issues/{id}/found`. `GET issues` is the transaction history: `status`, `state` (`on_loan`, `due_soon`, `due_today`, `overdue`), `member_id`, `book_id`, `copy_id`, `member_type`, `class_id`, `section_id`, `purpose`, `from`/`to` (issue date), `on` (issued or returned that day), sort `issued_at`, `due_date`, `returned_at`; `GET issues/export` is the same list as CSV. Each loan has `state`, `days_overdue` and `running_fine` (the late fine if returned today).

**Fines.** Late fine = late days after `grace_days` (Sundays and holidays skipped when `skip_holidays`) × `fine_per_day`, capped at `max_fine_per_book`; raised on return or when marked lost. Staff are fined only with `charge_staff_fines`. Lost = copy price + `lost_processing_fee`; found again waives what is unpaid. Damage = the amount entered at return. `fines` (`status`, `kind`, `member_type`, `class_id`, `outstanding`), `fines/insights`, `POST fines/{id}/payments` `{ amount, mode, reference?, paid_on?, notes? }` (receipt `TZMS-LIB-2026-0001`), `POST fines/{id}/waive` `{ amount?, reason }`, `fine-payments`, `fine-payments/{id}/receipt` (PDF). New loans are refused while unpaid fines exceed `block_issue_above_fine`. A student cannot get a TC while books or fines are pending (`409 LIBRARY_CLEARANCE_PENDING`).

**Follow-ups and alerts.** `GET follow-ups?show=due|all` lists overdue loans with no follow-up yet or whose next check date has come; `POST issues/{id}/follow-ups` `{ action, note?, promised_on?, next_follow_up_on? }` (actions `called_parent`, `reminded_student`, `reminded_staff`, `told_class_teacher`, `promised_date`, `other`). At 08:00 each loan walks the ladder once per step: `LIBRARY_DUE_SOON` (`due_soon_days` before), `LIBRARY_DUE_TODAY`, `LIBRARY_OVERDUE` (day 1), `LIBRARY_OVERDUE_ESCALATED` (after `escalate_after_days`, to the class teacher too, then weekly; SMS only if the push fails), `LIBRARY_OVERDUE_LONG` (after `long_overdue_days`, to the librarian and admin). Parents (with `receives_alerts`) get the student's notices; staff get their own. Also `LIBRARY_BOOK_ISSUED`, `LIBRARY_BOOK_RETURNED`, `LIBRARY_FINE_RAISED`, `LIBRARY_FINE_PAID` (category `library`). `POST reminders/run` sends the due steps now.

## Academic year

Meetings, diary posts, announcements and chats belong to the academic year they were created in. Every list (apps and admin web) shows only the **current** academic year; when the school switches to a new year, last year's history is no longer shown (the records stay in the database). An old record opened by id returns 404.

**Viewing an earlier year (admin web only).** On `/admin/*` routes the web may send `X-Academic-Year-Id: <id>` to see an earlier year: attendance, students (only those enrolled that year, with their class that year), exams and results, fees, diary, leave, timetable and the dashboard then use that year instead of the current one. Leave the header out (or send the current year's id) for normal use.

| Case                                        | Answer                                             |
| ------------------------------------------- | -------------------------------------------------- |
| Earlier year, `GET`                         | 200, that year's data                              |
| Earlier year, `POST`/`PUT`/`PATCH`/`DELETE` | 403 `YEAR_READ_ONLY` (earlier years are read only) |
| Year of another school                      | 404 `ACADEMIC_YEAR_NOT_FOUND`                      |
| Not a number                                | 400 `INVALID_ACADEMIC_YEAR`                        |

**Year status.** Every academic year has a `status`, with who and when for each step (`activated_at`/`activated_by`, `closed_at`/`closed_by`, `archived_at`/`archived_by`; the `_by` fields are names) and an optional `description`:

| Status     | Meaning                                                                                                                  | How it gets there                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| `draft`    | Planned, not started                                                                                                     | New year without `is_current`                                                   |
| `active`   | The current year (`is_current: true`); only one per school                                                               | `POST /admin/academic-years/{id}/activate` (or `PATCH` with `is_current: true`) |
| `closed`   | An earlier year: its dates and fee plans are locked, but dues can still be collected, discounted, cancelled and reversed | Automatically, when another year is activated; or restore from archived         |
| `archived` | Frozen: no fee changes at all, not even payments (409 `YEAR_ARCHIVED`)                                                   | `POST /admin/academic-years/{id}/archive`, only from `closed`                   |

`POST /admin/academic-years/{id}/restore` takes an archived year back to `closed`. An archived year must be restored before it can be activated. The active year cannot be archived; activate another year first. Dates of a new or edited year may not overlap another year (409 `YEAR_OVERLAPS`). Permission `schools.manage`. Existing years were set on upgrade: the current year `active`, years that ended before it `closed`, the rest `draft`.

`/mobile/*`, `auth/*` and `me/*` ignore the header: the Staff and Parent apps always show the current year.

**Year by year on the dashboard.** `GET /admin/dashboard/year-performance` returns `{ years: [...] }`, one row per academic year, newest first, up to the current year, so the office can compare years. Each row has `academic_year`, `studies` (published exams, average result %, pass rate, fail rate, % of papers absent), `attendance` (student %, students below 75%, staff %), `activities` (achievements, sports, podium finishes, students taking part, points, highest level), `students` (enrolled, promoted, left) and `fees` (billed, collected, collection %, and `heads`: the same for every fee head such as Tuition, Sports or Transport, biggest first; a payment is shared across its invoice lines by amount, and `is_transport` marks the bus fee). A section is `null` without its permission, the same as the dashboard. It lists every year whatever `X-Academic-Year-Id` says.

## Video meetings (Agora)

A teacher and a parent book a video call about one child. Either side can book it; both join from the app with `agora_rtc_engine`. The teacher is the **host**: only the host can extend or end the meeting. The admin web only lists meetings and their call log.

Lifecycle (example 10:00 to 10:30):

- Booking: `scheduled`, `MEETING_SCHEDULED` push to the other person, `MEETING_REMINDER` 10 minutes before the start.
- 09:50: join opens. The first join makes it `in_progress` and records the actual start.
- 10:25: `MEETING_ENDING` push and a `meeting.reminder` (`kind: ending`) event: show it inside the call.
- 10:30: the status becomes `time_exceeded`. **Nobody is disconnected**; people keep talking and can still join. The host can extend (`POST .../extend { "minutes": 10 }`, 120 minutes in total), which moves `ends_at` and sets it back to `in_progress`.
- The host ends it: `completed`, actual end and length saved, every attendance row closed, no new tokens, and the server asks Agora to remove everyone from the channel (kicking rule).
- A meeting nobody joins becomes `missed` 30 minutes after its end. A running meeting that everyone left more than 15 minutes ago, after its end time, closes itself as `completed` (`end_reason: empty`).

Tokens are short-lived (15 minutes). Renew with `POST .../token` on `onTokenPrivilegeWillExpire`; a completed meeting gets no new token (`409 MEETING_ENDED`). After a network drop, call `join` again: it records a new attendance row.

Every meeting has `from` (who booked), `to`, `teacher`, `parent`, `student`, `host_id`, `academic_year`, `ends_at` (with extensions), `extended_minutes`, `can_join`, `join_opens_at`, `join_closes_at` (only before it starts), `call_minutes` (actual length) and `end_reason`.

### When a meeting ends

| Case                             | What happens                                                                                                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Teacher presses End              | `completed`, `end_reason: host_ended`, straight away                                                                                                                                  |
| Everyone has left (cut the call) | `completed`, `end_reason: empty`, **5 minutes** after the last person left, even before the end time (rejoining within those 5 minutes keeps it open)                                 |
| Time is up                       | **10 minutes after the end time** (extensions included) it closes as `completed`, `end_reason: time_up`, the Agora channel is ended for everyone and Join returns `409 MEETING_ENDED` |
| Nobody joined                    | `missed` 30 minutes after the end time                                                                                                                                                |

### Agora uid

`POST …/meetings/{id}/join` returns `uid` = user id × 2 for the teacher side and user id × 2 + 1 for the parent side, so one person who is both teacher and parent can join from two phones without Agora kicking one off. Always use the `uid` from the join response; never build it from the user id.

### Accept or decline (like a Teams invite)

Whoever books a meeting, the **other side** gets it as an invite: `response` is `pending`, then `accepted` or `declined` (with an optional `response_note`).

| Call                                                     | Who                                          |
| -------------------------------------------------------- | -------------------------------------------- |
| `POST /mobile/teacher/meetings/{id}/accept` · `/decline` | Teacher, for a meeting the **parent** booked |
| `POST /mobile/parent/meetings/{id}/accept` · `/decline`  | Parent, for a meeting the **teacher** booked |

Body (optional): `{ "note": "Busy with exam duty" }`. The side that booked gets a push (`MEETING_ACCEPTED` / `MEETING_DECLINED`, category `meeting`, with `meeting_id`) and the `meeting.status` socket event now carries `response`.

- **Joining needs the reply `accepted`.** `can_join` is false while `response` is `pending` or `declined`; `POST .../join` returns `409 MEETING_NOT_ACCEPTED` or `409 MEETING_DECLINED`. Declining does not cancel; the booker can cancel or book another time.
- **No meeting with yourself:** a person who is both teacher and parent cannot book a meeting with themselves (`400 SAME_PERSON`). **Chat with yourself is allowed** (for example to share a file as the teacher with yourself as the parent). In the pickers (`/students/{id}/parents`, `/children/{id}/teachers`) that person comes with `is_me: true`: hide them when booking a meeting, show them for chat.
- A **declined** meeting does not hold the time slot: the same teacher and parent can book that time again.
- `join_closes_at`: for a meeting nobody has joined yet it is the **end time** (it becomes `missed` then); once it is live it is the end time + 10 minutes (hard stop).
- `in_call: { teacher, parent }` and `active_participants` (0, 1 or 2) show who is in the call right now. Ring only when the other side is in and you are not.
- When the **last person leaves** (`POST .../leave`), the meeting ends at once: `status: completed`, `end_reason: empty`, and any ring is cancelled. If someone drops without calling leave, it closes 5 minutes after the last activity.
- The reply can be changed (decline → accept) until the meeting starts.
- `403 NOT_MEETING_INVITEE` if the side that booked tries to reply; `409 MEETING_REPLY_CLOSED` once the meeting started, ended or was cancelled.
- Every meeting in lists and details has `response`, `responded_at`, `response_note`; `to` is the invited person.

### Incoming call ring and cancel

When one side joins (`POST .../join` succeeds) and the other side is not in the call, the API rings the other side. The joiner is never rung.

Ring and cancel arrive as a **data-only, high-priority push** (no title or body, every value a string) and as the socket event `meeting.call` with the same payload:

```json
{
  "category": "call",
  "event": "ring",
  "call_id": "c_8f21a3b4c5d6",
  "meeting_id": "11",
  "channel_name": "tzs_1_62b42c63d586b740",
  "caller_name": "Arun Prakash",
  "caller_role": "teacher",
  "student_name": "Harini Arun",
  "timeout_seconds": "45"
}
```

`caller_role` is the role of the person calling (pick the join endpoint for the **other** role on Accept). A `cancel` has the same `call_id` and fields plus `reason`:

| reason        | When                                                        |
| ------------- | ----------------------------------------------------------- |
| `answered`    | The rung side joined                                        |
| `declined`    | The rung side tapped Decline (`POST .../reject-call`)       |
| `caller_left` | The caller left before it was answered                      |
| `ended`       | The host ended the meeting, or it closed (empty or time up) |
| `timeout`     | Nobody answered in 45 seconds                               |

| Endpoint                                         | Who                                             |
| ------------------------------------------------ | ----------------------------------------------- |
| `POST /mobile/teacher/meetings/{id}/reject-call` | Teacher declines a ringing call from the parent |
| `POST /mobile/parent/meetings/{id}/reject-call`  | Parent declines a ringing call from the teacher |

- Accept = `POST .../join` as usual (it also sends `cancel` with `answered` to the caller's other devices).
- `reject-call` is safe to repeat; if the ring already stopped nothing happens. No body.
- One ring at a time per meeting. Rejoining while the other side is in the call does not ring.
- **Rings only the phone signed in for that side.** The ring and cancel go to the devices registered with `POST /me/devices` whose `app` matches the side being called (`staff` for the teacher, `parent` for the parent), never to every phone of the user. A person who is both teacher and parent is not rung on their Staff app for a parent call. Devices registered without `app` (or `mobile`) are used only when the user has no device for the other side. So the app must send `app: "staff"` or `app: "parent"` (the selected side) with `push_token` after login and whenever the user switches side.
- Delivery: `CALL_PUSH_DRIVER` (`kafka` → Notification Service template `school_call` with `dataOnly: true`, `data`, `priority: high`, `ttl`; `onesignal` → OneSignal data-only with `content_available`, `priority 10`, `include_aliases.external_id`; `fcm` → FCM data message, Android priority high). Empty = same as `PUSH_DRIVER`.
- iOS VoIP (PushKit through APNs) is not in this phase: it needs the Apple VoIP certificate.

## Chat (teacher and parent)

**Each academic year starts fresh.** Conversations belong to an academic year. When a new year becomes current, the earlier year's conversations are **soft-deleted** (hidden from the Staff and Parent apps, kept in the database) by an hourly job. Two years after that academic year ends they are **deleted for good** (messages and audit log too). A year created ahead of time is never touched.

The office can still read an archived year: `GET /admin/chat/threads?academic_year_id=<earlier year id>` lists it (each thread has `archived: true`) and `GET /admin/chat/threads/{id}` opens it read-only. One conversation per teacher, parent and child per academic year. Messages are saved first, then delivered live over `/comm` with a `CHAT_MESSAGE` push.

## Surveys and feedback forms

The school office builds a form with its own questions, sends it to chosen parents and staff, they answer once in the app, and the office sees the results. Teacher ratings and driver ratings stay as they are. `surveys.view` lists forms, results and the Excel; `surveys.manage` builds, sends, reminds, extends and closes, and manages ready-made forms. School admin and Principal have both.

**Questions.** `{ type, text, options?, is_required }`. `type` = `single_choice`, `multi_choice` (both need 2 to 10 different `options`), `rating` (1 to 5), `short_text` (up to 200 characters), `long_text` (up to 2000), `date` (`YYYY-MM-DD`), `number`. Other types take no options (400 `VALIDATION_FAILED` on `questions.<n>.options`). Up to 50 questions; sending `questions` replaces them all.

**Life of a form.** `status` = `draft` → `scheduled` (sent with `send_at`) or `open` → `closed` (at `closes_at`, or Close). Send fixes the list of people at that moment, one row per person with the app; with `per_child` a parent answers once for each child in the audience ("for Arun", "for Divya"), and a teacher who is also a parent answers once more as staff. People without the app cannot answer; the preview counts them in `without_app`. When it opens everyone gets `SURVEY_NEW` (push and in-app, never SMS). Once, 24 hours before `closes_at`, people who have not answered get `SURVEY_REMINDER` (skipped for a form open for less than a day); extending the close date arms it again for the new date, and Remind now sends it at any time. The first answer locks the form (`locked: true`): its questions cannot change any more, but Extend and Close still work. Answers cannot be changed after they are sent. With `is_anonymous` the school never sees who answered what (results, Excel and the not-answered list have no names, and written answers carry no class or section); the API still keeps who answered so nobody answers twice and reminders reach only those who have not.

**Audience.** The same choices as Emergency broadcast: `everyone`, `parents`, `staff`, `classes` (`class_ids`) or `sections` (`section_ids`). `staff_groups` narrows the staff part of `everyone` and `staff`: `teachers` (Teacher, HOD), `drivers` (bus crew: Driver and Attendant) and `office` (all other staff); empty means all staff.

## Gallery

Photo and video albums in three galleries: the **App Media Gallery** (`scope: school`, school-wide), the **Class-wise Gallery** (`scope: class`, one class of one academic year) and the **Section-wise Gallery** (`scope: section`). One set of tables serves the admin web, the Staff app and the Parent app. There is no student login, so students see the gallery through the Parent app.

**Who can do what.** `gallery.view` sees every album, the dashboard and reports. `gallery.manage` creates, edits, publishes and deletes in every gallery and restores from Trash. `gallery.configure` changes settings, retention policies and holds, runs and pauses the cleanup, and deletes for good. `gallery.audit` reads the audit log. School admin has all four, Principal has view, manage and audit, and the AO has view and manage. In the Staff app, a teacher (a role listed in the setting `upload_roles`, default Teacher and HOD) can add albums and upload only for current-year sections they teach or are class teacher of. A teacher manages their own albums, and a class teacher manages every album of their section. Teachers delete their own uploads only when `teachers_delete_own` is on. Albums of past years are read-only for teachers. Every check runs in the API.

**Who sees an album.** `status`: `draft` (the uploader and managers only), `published`, `archived` (hidden from parents, read-only, kept by the archived-albums policy). `visibility`:

| scope           | visibility                              | seen by                                                                         |
| --------------- | --------------------------------------- | ------------------------------------------------------------------------------- |
| school          | `everyone`                              | all staff and all parents                                                       |
| school          | `staff`                                 | staff only                                                                      |
| school          | `parents`                               | parents only (and gallery admins)                                               |
| school          | `classes` + `class_ids` / `section_ids` | parents of children in those classes or sections in the album's year, and staff |
| class / section | `everyone`                              | parents of children in that class or section that year, and its teachers        |
| class / section | `staff`                                 | its teachers only                                                               |

A parent sees an album only if a linked active child was in that class or section in the album's academic year, including earlier years. Albums they cannot see return 404 `ALBUM_NOT_FOUND`. When the school switches off the gallery (`is_enabled`) or one gallery (`app_gallery_enabled`, `class_gallery_enabled`, `section_gallery_enabled`), staff and parents get 403 `GALLERY_DISABLED` / `GALLERY_SCOPE_DISABLED`, while admins can still see and tidy it.

**Uploading.** `POST .../albums/{id}/media` as `multipart/form-data` with one or more `files` (at most `max_files_per_upload`, default 20) and optional `checksums` (SHA-256 of each file in order; a mismatch fails that file with `CHECKSUM_MISMATCH`). The API checks the real file content, not the name: JPEG, PNG and WebP photos; MP4, MOV, WebM and 3GP videos, as allowed by `image_formats`, `video_formats` and `videos_enabled`. Photos are auto-rotated, resized to `image_max_side` (2048), compressed at `image_quality` (82) and stripped of all EXIF, GPS, XMP and IPTC metadata. Originals are not kept. Each photo gets a `thumbnail_side` (400) WebP thumbnail. For MP4, MOV and 3GP videos, the length is read from the file (`VIDEO_TOO_LONG` above `max_video_seconds`) and the location and metadata boxes are blanked. The server makes no video frames: the app takes a still and sends it with `PUT .../media/{id}/poster` (field `file`). The same file twice in one album is skipped as a duplicate. When storage is full, uploads fail with `STORAGE_FULL`. The reply always comes back 200 with per-file results, so retry only the failed ones:

**How the automatic cleanup works.** Defaults: on; retention **1 year from the upload date**; daily at 02:00 in `time_zone` (Asia/Kolkata); 30 days of notice; 30 days of recovery; permanent deletion on. `cleanup_frequency` can be `daily`, `weekly` (`cleanup_weekday` 1 = Monday) or `monthly` (`cleanup_month_day` 1 to 28). Each run, per school:

1. Recalculates every item's `expires_at` from the policies (`retention_source` says which rule applied; `null` means kept forever).
2. Takes items off the schedule if a hold or a longer policy now covers them (`unmarked`).
3. Marks items whose retention ends within `notice_days` as `pending_deletion`, with `trash_at` no earlier than now + notice (so an item is never trashed without notice, even if it expired long ago), and sends `GALLERY_DELETION_SCHEDULED` to `notify_roles`. Held items are skipped and counted in `held`.
4. Moves marked items whose `trash_at` has passed to Trash (`deleted_reason: retention`, `purge_after` = now + `recovery_days`), and albums left empty by that (`delete_empty_albums`).
5. With `permanent_delete_enabled`, deletes Trash items past `purge_after` for good, with their stored files and thumbnails (held items stay), then empty albums past theirs. Failures stay in Trash, are listed as `failed` items and can be retried.
6. Removes stored files left behind by failed uploads (`purge_orphans`) and upload records older than 30 days (`purge_stale_uploads`).
7. Records the run and every item, writes the audit log, sends `GALLERY_CLEANUP_DONE` (when something changed) or `GALLERY_CLEANUP_FAILED`, and checks storage.

With `auto_trash_enabled` off, nothing is marked or trashed automatically. ## Inventory and assets (admin web)

Everything is under `/admin/inventory/*` (Swagger tag `Admin · Inventory`). Permissions: `inventory.view`, `inventory.manage` (assets, allocations, masters), `inventory.stock` (receipts, issues, adjustments, stock items), `inventory.approve` (transfers, disposals, requisitions) and `inventory.audit`. The new **Store Keeper** role (demo `9000000012`) has view, manage, stock and audit; Principal and AO approve.

**Assets.** `POST assets` registers one or more identical assets (`quantity`, `serial_nos`), each with its own tag `TZMS-AST-000001`. `status` is `in_store`, `allocated`, `in_maintenance`, `lost` or `disposed`; `GET assets?status=in_store,in_maintenance` takes several values separated by commas. Each asset carries `book_value` (straight-line or written-down depreciation, set in `settings`), `warranty_state` and `current_allocation`. `PATCH assets/{id}` can clear `purchase_date`, `warranty_until` and `amc_until` with `null`. `GET assets/{id}/history` is the full event trail. `GET assets/lookup?code=` finds an asset by tag or serial number (for scanners), `GET assets/labels` returns a PDF of Code 128 tag labels, and `POST assets/import` (multipart `file`, `mode=validate|import`) reads the Excel template from `GET assets/import/template`; each report row has `asset_tags` and `asset_ids`. Dates must be real calendar dates (`YYYY-MM-DD` or `DD-MM-YYYY`); anything else is reported on that row.

**Allocation.** `POST allocations` assigns assets to a staff member (`user_id`), a department or a location, with an optional `expected_return_on`. `POST allocations/return` takes them back, optionally straight to maintenance. Staff see what they hold at `GET /me/assets` (each with `allocated_on`, `expected_return_on`, `overdue`, `days_overdue`, `acknowledged_at` and the store keeper's `remarks`), what they returned at `GET /me/assets/history` (last 50, with `returned_on` and `return_condition`), and confirm receipt with `POST /me/assets/{allocationId}/acknowledge` (409 when already confirmed, 404 for someone else's). These work in every app; a parent gets an empty list. Asset pushes (`category: inventory`) carry `role: driver` for drivers and attendants and `role: staff` for everyone else, so the tap opens the right app; `INVENTORY_ASSET_ASSIGNED` and `INVENTORY_RETURN_DUE` open My assets. A staff member who still holds assets cannot be marked resigned or deleted (409 `ASSETS_PENDING`).

**Transfers and disposals.** `POST transfers` and `POST disposals` create requests; when approvals are on in `settings`, someone with `inventory.approve` calls `.../approve` or `.../reject`. An allocated asset must be returned before it is disposed of (`ASSET_ALLOCATED`). While a transfer is open, the asset cannot be allocated, marked lost or sent for disposal (`ASSET_IN_TRANSFER`); approve, reject or cancel the transfer first.

**Maintenance.** Tickets (`maintenance`) move `open` → `in_progress` → `resolved`/`cancelled`; the asset is `in_maintenance` while one is open. `schedules` hold preventive work with `next_due_on`.

**Stock.** Consumables are valued at weighted average cost. `stock/receipts` (goods received; sort `received_on`, `receipt_no`, `total`, `vendor`), `stock/issues`, `stock/adjustments` and `stock/movements` (the ledger). `requisitions` go `pending` → `approved` → `issued`/`partly_issued`. Issuing more than the store holds is refused with `NOT_ENOUGH_STOCK`.

**Audits.** Asset verification by scanning tags (`audits/{id}/scan`: `found`, `misplaced`, `not_available`, `unknown`) or a stock count (`audits/{id}/count`); closing can mark missing assets lost or post count differences as adjustments.

**Reports.** `reports/assets?group_by=category|location|department|custodian|status`, `reports/depreciation`, `reports/maintenance`, `reports/consumption`, `reports/stock-valuation`. `reports/register/export` (CSV) takes the same filters as `GET assets`; `reports/movements/export` exports the stock ledger.

**Masters.** `categories` (asset or stock, depreciation rate or useful life, maintenance interval), `locations` (`locations/sync-rooms` creates them from timetable rooms), `departments` (`departments/sync` creates them from staff departments), `vendors`, `stores`. Deleting something in use returns `*_IN_USE`; a duplicate code returns `*_EXISTS`.

**Alerts.** A daily job at 08:15 sends overdue-return reminders to staff and maintenance-due, warranty/AMC-ending and (on Mondays) low-stock summaries to the store office. `POST alerts/run` runs it now.

## Staff Performance Reviews & Appraisals (Module 3.3)

The school appraises staff once (or more) a year in **cycles**. Staff are placed in **appraisal groups** (teams) for the academic year; each group has its **own KRA set** (Key Result Areas, weights adding up to 100). Flow: the office opens a cycle → each person scores themselves in the Staff app → the **HOD** of their department scores → the **Principal** gives the final score and publishes → the person acknowledges or appeals.

Permissions: `appraisals.view` (see everything), `appraisals.configure` (groups, KRAs, cycles), `appraisals.finalize` (final score, publish, appeals). Principal: all three; AO: view + configure; Admin: all. The Staff app routes are `/me/*` and work for every staff member (office staff too).

**Groups.** `rules` = `{ staff_types: ['teaching'|'non_teaching'], departments: [], designations: [], roles: ['TEACHER', 'HOD', …] }`: every kind that has values must match; within a kind any value matches (case-insensitive). People can also be **included** or **excluded** by hand. A person goes to the group they are included in, else the first matching group by `sort_order`, else the `is_default` group (the catch-all, which needs no rules). `GET …/members` shows who is in the group today and who also matches it but sits in another group.

**KRAs.** `{ code, title, description?, category, weightage_percent, max_score (2–10, default 5), scoring_mode: manual|auto, auto_metric?, auto_target? }`. Auto KRAs are scored from school data of the academic year: `attendance_percent` (staff check-in), `exam_pass_percent` (published exams of the classes and subjects taught), `parent_rating` (average stars, Parent app), `parent_good_behaviour_percent`, `homework_count` (published diary homework), `driver_rating`. Auto score = `min(max_score, value ÷ auto_target × max_score)`; the default target is 100 for percentages, 5 for ratings and 60 for homework. When there is no data the person scores it by hand.

**Percent and rating.** KRA % = score ÷ max_score × 100; overall % = Σ KRA % × weight ÷ 100 — computed on the server for self, HOD and final. Rating on the final %: ≥92 `outstanding`, ≥76 `exceeds_expectations`, ≥60 `meets_expectations`, ≥40 `needs_improvement`, else `unsatisfactory`. `suggested_increment` comes from the cycle's `increment_bands`; the Principal sets `increment_percent`. Recommendation defaults to `pip` for the two lowest ratings, else `increment`.

**Steps (`stage`).** `self_pending` → `hod_pending` (skipped when the department has no HOD, or the person is an HOD or the Principal) → `principal_pending` → `published` → `completed` (acknowledged) or `appealed` → `completed` (appeal decided). At `self_due_at` the reviews still at `self_pending` move on with `self_missed = true`. Reminders: staff 24 h before `self_due_at`, HODs 24 h before `hod_due_at` (or on demand with `/remind`). Push templates: `APPRAISAL_SELF_OPEN`, `APPRAISAL_SELF_REMINDER`, `APPRAISAL_HOD_REVIEW`, `APPRAISAL_HOD_REMINDER`, `APPRAISAL_PUBLISHED`, `APPRAISAL_APPEAL_RAISED` (Principal), `APPRAISAL_APPEAL_DECIDED`; `data.appraisal_id` opens the appraisal (`category: approval`).

## Alumni records (admin web)

Admin endpoints are under `/admin/alumni/*` (Swagger tag `Admin · Alumni`). Permissions: `alumni.view` (list, profile, reports) and `alumni.manage` (edit, update links, approve submissions). Staff never create alumni by hand: students become alumni when they leave. School admin and Principal have both; the AO has `alumni.view`.

**How people become alumni.**

- **Automatically at year close.** When an academic year stops being current (another year is created as current, or made current), every student in the final class (the class with the highest `grade_level`) whose enrolment is still `studying` passes out:
  - the student's `status` becomes `alumni` and `left_on` is the year's end date;
  - the enrolment becomes `completed`;
  - an alumni record is made (`source: pass_out`, `exit_type: graduated`, batch = year of the end date), with their class history, final percent, grade and result, and the primary guardian's mobile, email and address as starting contact details.
  - Students marked `detained` in promotion stay. Fee dues do not block pass-out; they stay on the student. Running it twice does nothing extra.
- **When a TC is issued.** After the NOC is cleared, `POST /admin/students/:id/exit` (transferred or withdrawn) also creates the alumni record in the same transaction (`source: converted`), using the TC for exit type, leaving date, TC number and last class, plus class history and results. Students who already had a TC before this module were added once by the migration `AlumniFromTransferCertificates`.
- **Self-registration:** the public form below, for people who left before the school used this system; staff approve it first.
- Every route copies the student's `emis_number` to the alumni record. Alumni items and details return `emis_number`; `PATCH /admin/alumni/:id` accepts it (max 50). Existing alumni linked to a student were filled once by the migration `AlumniEmisNumber`.
- `PATCH /admin/students/:id` with `status: alumni` is refused with `400 ALUMNI_STATUS_MANAGED`. `GET /admin/students/:id` now returns `left_on` and `alumni_id`.

**Endpoints.**

- `GET /admin/alumni`: paginated list. Filters `batch_year`, `source` (`pass_out`, `converted`, `registered`, `self`), `exit_type` (`graduated`, `transferred`, `withdrawn`), `occupation_status` (`higher_studies`, `employed`, `self_employed`, `seeking`, `other`, `unknown`), `status` (`active`, `inactive`), `reachable` (consent plus a mobile or email), `city`. Search covers name, alumni no, admission no, EMIS number, mobile, email, institution, organisation and city. Sort: `name`, `batch_year` (default), `left_on`, `final_percent`, `alumni_no`, `created_at`.
- `GET /admin/alumni/insights`: `total`, `active`, `reachable`, `latest_batch`, `pending_submissions`, `by_occupation`, `by_batch` (last six).
- `GET /admin/alumni/batches`: `[{ batch_year, count }]`, newest first.
- `GET /admin/alumni/pass-out-preview?academic_year_id=`: the final class, who will pass out when that year closes (with percent and unpaid fees), and how many are detained or already alumni. Defaults to the current year.
- `GET /admin/alumni/export`: Excel file with the list filters.
- `GET /admin/alumni/:id`: profile with `academic_history` (rows with `source: system` were copied from school records and are read-only; `manual` rows are editable), `timeline` (every change as `{ field: [before, after] }`) and `pending_submissions`.
- `PATCH /admin/alumni/:id`: update the profile; every changed field is written to the timeline.
- `PUT /admin/alumni/:id/academic-history { rows }`: replaces the manual rows.
- `PATCH /admin/alumni/:id/status { status, note? }`: `inactive` means do not contact.
- `DELETE /admin/alumni/:id`: soft delete; the student keeps `alumni` status.
- `POST /admin/alumni/:id/update-link`: returns `{ path, expires_at }`. Prefix `path` with the admin web address and send it to the alumnus. It lasts 14 days, works once, and replaces earlier links.
- `GET /admin/alumni/submissions?status=&type=`: self-registrations and self-updates. Updates carry `changes` (`[current, submitted]`); registrations carry `possible_matches` (same mobile, or same first name and batch).
- `POST /admin/alumni/submissions/:id/approve { alumni_id? }`: a registration creates a record (`source: self`), or with `alumni_id` merges its contact and career details into that record; an update applies its changes. `409 SUBMISSION_CLOSED` if already handled.
- `POST /admin/alumni/submissions/:id/reject { note }`.

**Public endpoints (no sign-in, Swagger tag `Public · Alumni`).**

- `GET /public/alumni/schools/:code`: school name and logo for the form header.
- `POST /public/alumni/schools/:code/register`: `first_name`, `batch_year` and a `mobile` or `email` are required, plus optional identity, contact and career fields. Responds with `{ id }`.
- `GET /public/alumni/update/:token`: the alumnus's contact and career details.
- `POST /public/alumni/update/:token`: sends changed contact and career details for approval and uses up the link. `400 NO_CHANGES` if nothing changed.
- Only contact and career fields can be changed this way; staff notes, results and history cannot. Unknown fields are refused. Limits: three pending submissions per mobile (`409 SUBMISSION_PENDING`) and 50 public submissions per school per hour (`429 TOO_MANY_SUBMISSIONS`). Expired or used links give `404 LINK_INVALID`.
- Admins and the Principal get an `ALUMNI_SUBMISSION` notification for each new submission.
